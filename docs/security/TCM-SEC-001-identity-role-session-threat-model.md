# TCM-SEC-001｜身份、邀请、角色、会话与威胁模型

- 版本：0.2
- 状态：Synthetic Prototype Under Review / Not Production Ready
- 日期：2026-08-03
- 上游：MAP-002、MAP-004、MAP-PROD-001

## 范围与结论

本基线把“医生推荐加入、患者由医生邀请、医生与患者智能体建立受控连接”转化为最小安全合同。当前 Alpha 仍只使用合成身份，不实现真实登录或保存资质证件；真实试点必须另行完成生产身份、密钥、部署和合规审查。

核心原则是：**邀请只允许申请加入，身份核验决定角色，照护关系决定数据范围，患者同意决定处理目的，医生签署需要再次验证。** 任一环节都不能替代其他环节。

## 0.2 合成原型实现

`map_tcm.identity.IdentityAccessService` 已把本基线实现为仅供自动化验证的 SQLite 状态机：

- 邀请明文令牌只在签发时返回一次，数据库只保存 SHA-256 摘要；
- 接受邀请后主体进入 `identity_pending`，不会获得医生签署能力；
- 安全管理员核验、医生合成资质状态和账户激活分别记录；
- 医生只能申请关系，必须由患者会话再次验证后接受并授予目的/字段范围；
- 访问决策使用服务端主体角色，忽略客户端自称角色；
- 关系、同意、字段、对象状态、近期再次验证与会话撤销逐项检查；
- 允许与拒绝均写入不包含秘密和临床正文的审计事件。

当前只开放不含身份、邀请或令牌材料的 `GET /api/v1/security` 计数视图。签发、核验和授权方法尚未暴露为公开 HTTP 写接口，也尚未替换现有合成工作台的演示型 `actor_role` 参数。这是刻意的安全 Gate：在真实身份提供者、安全 Cookie/CSRF、密钥、部署与专项评审完成前，不得把该原型表述为生产登录或真实临床授权系统。

## 主体与角色

| 角色 | 默认能力 | 明确禁止 |
| --- | --- | --- |
| `patient` | 管理自身资料与同意；提交事实和反馈；查看获授权摘要 | 读取他人资料；签署医生判断；让 AI 代为同意 |
| `verified_doctor` | 在有效照护关系内采集、编辑、评审和签署 | 跨关系浏览；把权限转交智能体；伪造患者陈述 |
| `care_executor` | 查看执行任务所需最少计划；记录实际执行和异常 | 制定/修改处方；签署辨证；查看完整病历 |
| `clinic_admin` | 账户、邀请、关系和安全事件配置 | 默认读取或修改临床正文 |
| `founder_operator` | 治理配置和去标识化试点质量 | 默认读取临床正文；替医生作临床决定 |
| `knowledge_steward` | 管理来源、版本、主张和争议 | 查看未授权私人病历；发布临床处方 |
| `delegated_agent` | 在主体明确授权的能力范围内整理、检索和起草 | 同意、签署、邀请、提权或自主诊疗 |

角色不能只由客户端提交的字符串决定。生产系统必须从服务端会话读取主体、核验状态、机构和授权能力，再对每个对象执行关系级检查。

## 邀请与加入状态机

```text
issued
→ accepted
→ identity_pending
→ active
→ expired / revoked / rejected / suspended
```

每份邀请必须绑定：不可预测的一次性令牌哈希、预期角色、邀请者、预期接收对象或通道、目的、签发与失效时间、最大使用次数、撤回状态和审计引用。

### 医生加入

1. 只有获准推荐的 `verified_doctor` 或安全管理员可发出医生申请邀请。
2. 接受邀请只建立 `identity_pending` 账户，不能获得医生签署能力。
3. 资质核验由独立流程完成，记录法域、资质类型、核验来源、有效期和核验者；证件原件不进入代码仓库。
4. 只有 `verified + active` 的医生会话可以签署；资质过期、暂停或关系失效立即阻断新签署。

### 患者加入与照护关系

1. 医生邀请患者只能创建关系申请，不能替患者同意。
2. 患者接受后明确选择目的、资料范围、有效期和可访问成员，关系才变为 `active`。
3. 结束关系不删除依法需要保留的记录，但停止新的非必要访问与共享。
4. 多医生会诊使用多个独立授权关系；一位医生的邀请不自动授权其他医生。

### 治疗执行者加入

治疗执行者由患者明确授权，并由负责医生发布任务范围；权限同时受患者、计划、字段和时间约束。家庭照护者与专业治疗人员使用不同资质标签，但都不继承医生权限。

## 权限决策

每次访问按以下顺序执行，任一条件失败即拒绝：

```text
已认证主体
→ 账户与资质状态有效
→ 角色拥有该能力
→ 与对象存在有效关系
→ 患者同意覆盖当前目的和字段
→ 对象状态允许该操作
→ 高风险操作完成近期再次验证
→ 写入审计事件
```

高风险能力至少包括：`clinical_record.sign`、`consent.change`、`care_relationship.change`、`invitation.issue`、`bulk_export.request` 和 `role_or_verification.change`。

## 会话基线

- 浏览器会话使用 `Secure`、`HttpOnly`、`SameSite` Cookie；认证令牌不得存入 `localStorage`。
- Web 写操作必须防 CSRF；登录、邀请接受、签署和导出必须防重放。
- Alpha 候选值：空闲 30 分钟、绝对 12 小时；生产值由风险和使用测试确定。
- 签署、同意变更、关系变更、邀请和导出要求最近 10 分钟内再次验证。
- 登出、密码/凭据重置、账户暂停和安全事件必须撤销服务端会话。
- Cookie、邀请令牌、证件、访问令牌和患者资料不得进入日志、URL 查询串、Git、CI 产物或前端分析事件。

## 威胁与控制

| 威胁 | 主要控制 | 必测负向场景 |
| --- | --- | --- |
| 邀请链接被转发或猜测 | 高熵一次性令牌、接收对象绑定、短有效期、撤回 | 第二次使用、过期、错误接收人均拒绝 |
| 未核验者冒充医生 | 独立资质状态；服务端能力；签署再次验证 | `identity_pending` 无法签署 |
| 横向越权读取患者 | 对象级照护关系和同意检查；不可枚举 ID | 医生不能读取非关系患者 |
| 运营或管理员浏览病历 | 管理面与临床面分离；break-glass 审批 | admin 默认无正文读取权 |
| AI 或客户端伪造角色 | 忽略客户端角色声明；服务端会话派生 | `actor_role=doctor` 不能提权 |
| 会话窃取/重放 | 安全 Cookie、CSRF、轮换、服务端撤销 | 登出后的会话和旧请求被拒绝 |
| 多模态文件恶意载荷 | 类型/大小检查、隔离扫描、元数据清理 | 双扩展、超限和不支持格式拒绝 |
| 提示注入或模型外泄 | 最小字段、工具白名单、输出审查、无自主写入 | 文档指令不能触发导出/签署 |
| 审计被篡改 | 追加式事件、完整性链、权限隔离和导出校验 | 关键事件缺失导致验收失败 |
| 评价、分享或邀请骚扰 | 受众控制、频率限制、举报封禁和证据保全 | 封禁者不能继续邀请或联系 |
| 紧急症状被健康助手淡化 | 明确非急诊边界、人工升级和审计 | 高风险信号不输出自主处理方案 |

## 必须审计的事件

- 登录成功/失败、会话签发/轮换/撤销；
- 邀请签发、接受、拒绝、过期和撤回；
- 身份/资质核验、暂停和恢复；
- 照护关系与执行任务的建立、变更和终止；
- 同意授予、变更、撤回与目的校验失败；
- 临床资料读取、写入、评审、签署和撤回；
- 导出、分享、批量查询、权限变化与 break-glass；
- AI 工具调用、拒绝、越权尝试和安全升级。

审计事件至少记录事件 ID、主体、服务端角色、能力、对象、目的、决定、原因码、会话 ID、时间、来源应用和关联请求 ID；不得记录秘密或非必要临床正文。

## Alpha 验收门

0.2 已完成安全状态机的合成原型与负向测试，不代表真实身份功能可用。进入受控生产集成前必须满足：

1. 邀请、核验、关系、同意和会话分别建模；
2. 权限由服务端主体与对象关系决定，而非请求体角色字符串；
3. 负向测试覆盖跨患者访问、未核验签署、客户端角色提权、邀请重放/过期/错绑、管理员与代理越权、字段超范围、同意撤回和会话撤销；
4. 关键写入与读取产生可查询审计；
5. 威胁模型经安全、临床和隐私评审；
6. 身份提供者、真实资质核验、安全 Cookie/CSRF、密钥、部署、备份和事件响应完成专项设计；
7. 临床 HTTP 写接口改为只接受服务端会话上下文，并完成端到端负向集成测试。

在这些条件完成前，现有工作台和评审门户继续标记为 `synthetic_only`，不得接入真实患者资料。
