## 目的

本文件把 Founder 从医生、患者和运营治理三方提出的业务愿景转化为可追踪的产品需求。它不改写原始文档，不替代 MAP-000 至 MAP-008，而是建立从原始思想、产品边界到工程任务的桥梁。

## 原始业务模型

平台以“天—地—人”和“患—医—治”为两组核心关系：时间、节气、地点与环境构成健康上下文；患者陈述与长期变化、医生辨证与方案、治疗执行与反馈形成循环。AI 处于三方之间，负责多模态整理、结构化记录、检索、比较、提醒和可审查草稿。

```text
患者事实与目标
→ 医生采集与辨证
→ 医生确认的干预方案
→ 获授权的执行者实施
→ 患者反馈与结局观察
→ 进入下一次记录和复诊比较
```

知识系统由彼此独立的个人健康智能体和医生智能体节点组成，不设共同知识体。各节点共同遵循经典来源、版本、授权、交换与审计协议，只在明确目的下点对点交换可追溯知识信封。

### 治疗执行者

“治”表示执行经医生确认的干预计划，可以是医生、受资质约束的治疗人员、患者本人或获授权照护者。该角色不自动获得医生权限。

| ID | 需求 | 安全解释 |
| --- | --- | --- |
| CARE-001 | 只查看执行当前任务所必需的方案内容 | 患者同意、医生发布、最小字段和有效期限缺一不可 |
| CARE-002 | 记录是否执行、实际暴露、时间、偏差和异常 | 记录事实，不修改医生判断或签署记录 |
| CARE-003 | 出现加重、不良事件或不确定性时升级现实医生 | 不允许执行者或 AI 自行变更处方和高风险方案 |

## 关键语义校准

以下校准保留 Founder 愿景，同时使产品可安全落地：

1. **“患者成为自己的医生”**在产品中表示健康素养、自我观察、生活方式管理和在医生指导下执行低风险计划，不表示患者智能体可独立诊断或处方。
2. **“知识库是辨证施治的主体”**表示每个独立智能体知识库承担该节点的记忆、证据组织、比较和持续学习；不存在代表所有人的共同大脑，现实医生仍是临床决定、沟通与签署主体。
3. **“代码即法律”**表示已批准的权限与治理规则应由代码一致执行；代码不能越过适用法律、患者同意、临床责任和高风险人工审查。
4. **患者或照护者可以执行治疗**不等于其拥有制定或修改处方的权限；系统必须区分 `plan_author`、`plan_approver` 和 `care_executor`。
5. **医生评价**与临床结局、投诉和社区互动分开建模，避免人气分数冒充疗效证据或形成骚扰工具。

## 当前验收与开放问题

- 原始 DOCX 与 PDF 正文实质一致；PDF 共 6 页，页面与图表未见裁切。
- 本基线不宣称临床确认；初诊/复诊字段仍由 TCM-CLIN-001 的 2–3 名合作医生评审决定。
- 需要后续明确：医生资质核验法域、治疗执行者的资质分类、公开分享范围、紧急升级路径、农历/节气数据来源、药材价格数据的合法来源与更新责任。
- 任何真实患者数据、公开社区、外部模型或自动健康建议仍受独立 Gate 控制。
