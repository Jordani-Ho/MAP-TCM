# MAP-DEV-013：动态健康时间线与四时环境上下文 0.1

状态：`Engineering Pre-review Complete / Synthetic Only`

## 结论

TCM-ENG-005 已形成第一套可运行的合成工程基线：把饮食、睡眠、二便、情志、活动、穿衣冷热、身体感受、气候、季节、节气、地点抽象和居住环境作为有来源、可排序、不可原位改写的健康观察，组织进患者本人私域的动态时间线。

本实现只回答“在什么时间、什么环境下，观察到了什么，以及信息来自哪里”，不回答“为什么发生”，更不自动形成辨证、诊断、处方或疗效结论。时间先后不等于因果关系；医生判断仍进入独立临床记录并由真人医生审核签署。

## 一、三层连接

每条结构化观察同时连接：

1. `PatientVaultEntry`：保留患者私域中的来源事实、内容哈希和合成来源引用；
2. `PatientHealthTimelineEvent`：提供统一发生时间、事件类别、来源角色和确认状态；
3. `HealthContextObservation`：提供观察类型、明确未知状态、起止时间、时区、地点抽象及无临床权限标记。

三层在同一事务追加。最后一步失败时，来源、时间线、结构化观察和审计全部回滚，不留下半条事实。

## 二、观察词汇

### 人的日常观察

- 饮食；
- 睡眠；
- 二便；
- 情志与压力；
- 活动；
- 穿衣与冷热感受；
- 身体感受。

### 天地环境上下文

- 气候；
- 季节；
- 节气；
- 地点抽象；
- 居住环境。

这些词汇是工程候选，不是临床标准。后续仍需中医师判断哪些观察在真实接诊、随访和“治未病”学习中最有用，以及应以什么顺序和粒度呈现。

## 三、未知与拒答

`observed / unknown / not_collected / not_applicable / declined` 是一等状态。只有 `observed` 可以携带结构化内容；其余状态必须保持空值，系统和 AI 不得根据上下文补写“正常”或猜测内容。

## 四、来源与时间

- 来源限于患者、医生、文件、设备和系统；
- 来源角色必须与患者陈述、医生确认、外部文件、设备记录或系统记录状态严格配对；
- 起止时间必须是带时区的 ISO 时间，服务端统一归一到 UTC 排序，同时保留时区名称用于展示；
- 窗口读取只做确定性时间排序和类型过滤，不计算因果或临床趋势。

## 五、四时与节气边界

首版不在代码内宣称某个公历时刻必然对应某个节气。系统记录节气时，必须同时保存节气标签、计算方法和历法版本。农历、节气、天气、气候区和地理数据源在获得真人技术、临床及法律审查前不得接入生产。

## 六、地点与隐私分层

患者本人私域的原始来源层未来可以依法保存精确出生地、居住地或其他本人资料；但动态健康时间线只复制临床/观察所需的气候区域或城市级抽象，不复制街道地址、经纬度、GPS、坐标或邮编。这样既不否认患者私域的完整性，也避免每条日常观察重复暴露精确定位。

## 七、不可变与安全边界

- 时间线事件和结构化观察均由数据库触发器禁止更新或删除；
- 更正必须以后续来源事实和新事件追加，不覆盖历史；
- 每次持久化写入形成不含患者叙述的最小审计；
- `causal_inference=false`、`clinical_authority=false` 固化在数据库；
- 结构化内容拒绝诊断、处方、治疗建议和因果结论键；
- 当前仅接受 `SYN-*` 合成患者与 `synthetic://` 来源。
